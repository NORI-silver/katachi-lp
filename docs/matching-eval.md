### 直したこと
1. 会社の工程の付け方（`tools/capwords.py`、企業DBの `katachi/capwords.py` と同じ中身）：国の登録情報だけの会社は説明文の言葉で工程を付けていて、
   「ジャパン」「カンパニー」「パンフレット」→加工食品、「靴下」→革製品、「シールド工法」→ラベル印刷、「半導体シリコン」→シリコーン成形、「ガソリンスタンド・鈑金塗装」→金属製品 などの誤りが多かった。
   短いカタカナ・英字の言葉は前後の区切りを見る、長い言葉の中の短い言葉は使わない、「◯◯用」「◯◯付属金具」「包装機械」などは除く、で読み直した。
   ほかの会社にも、説明文から読める工程を足した（「バッジのOEM」が衣料だけ、「がま口のバッグ」が雑貨だけ、など）。
2. 依頼文の読み方（`analyzeText`）：長い言葉の中の短い言葉は読まない（「ドリップバッグ」→革製品、「ジャーキー」→容器を防ぐ）。
   「ロゴ入り・名入れ」だけのプリントの工程は布の物のときだけ。「キャンプ・アウトドア」など使う場面の言葉だけの雑貨の工程は、ほかに作る工程があれば外す。
   「機械を載せる架台」のように機械が相手として出るだけなら機械の依頼にしない。「オリジナルデザイン」で設計の工程を足さない。石けん・コーラ・ドリップバッグ・ピンバッジなどの言葉を足した。
3. 依頼との近さ（`relTerms`・`relOf`）：カタカナの切れ端（「ケー」「ブラン」）を使わない。同じ言葉を何度も数えない（「ケース」がキーケース・カードケースで3回など）。
4. 設計の相談先（`dsRows`）：依頼の品の言葉が説明に出る会社を、確かさ・所在地より先に。
5. 完成品メーカーに「看板・サイン」を足した（LEDの看板が電子機器のODMになっていた）。

### 残っている△
- 長い仕様文（車載リフト）：工程が細かく割れ、海外の電子部品の会社が付く。
- 犬の車椅子・Bluetoothスピーカー・ドリップコーヒー・リュック・電動台車・アクリルケース・トート・子供服・スタイ：工程は合うが、その品を作ると書いた会社がDBに少ない／上に来ない。品目の会社の収集が要る。
- （2026-11-15 直した）APIの search_companies も、サイトの fitOf（依頼との近さ・業態・分野・規模・所在地）を `api/build.mjs` が template.html から取り出して使う。製品12品で、上位3社が品の会社になったのは 直す前 ほぼ0 → 11品。

## 直したこと（`tools/template.html`）
1. 依頼の中身との近さ（`relBuild`・`relOf`）：依頼文と製品名の言葉が社名・説明に出るかを、言葉の珍しさ（IDF）で重みづけ。カタカナの語は語の途中に当てない。
2. 外の注文を受ける業態（OEM・受託・試作・小ロット・オーダー等）を上げ、土木・不動産・卸だけの会社を下げる（`fitOf`）。
3. 依頼にない分野（食品・化粧品・衣料・電子など）を持つ会社を下げる。少量の依頼で従業員300人超・1,000人超（国の公開データ）を下げる。
4. 文章の都道府県（届け先を選べばそれも）と同じ県・地方を上げる。1台だけ・体に合わせるものは強く。完成品メーカーも近い順。
5. 一社案：OEMの会社は包装の工程も受けるとみなし（`capCovers`）、依頼に合わない会社は窓口にしない。
6. 電子機器ODMを★にするのは、製品そのものが電子機器のときだけ。回路図・部品表があって「実装」を頼むときは設計の工程を足さない。
7. 長い仕様文は「将来の機能」「初期は不要」を読まず、【見出し】が多いときは製品名・構成・外観・材質などの節だけで工程を読む（`specCore`）。

## 残っている外れと次の一手
- 長い仕様文（車載リフト・ソファ用スロープ）は、キーワードで工程を読むため関係ない工程（GPS・縫製など）が残り、組み合わせが細かく割れる。仕様文の読み取り（スレッド「自然な文章を工場向けの仕様に翻訳する」）と合わせて直す。
- 企業DBにいない／工程が付いていない会社：結城工業（船橋、ワンオフ溶接）は未収録、コムラ製作所（八尾、介護福祉機器）は工程の言葉がなく画面に出ない。スロープ・昇降機・焚き火台などを作る会社の収集が要る。
- 読み取りの誤り：什器→ガラス、指輪→ウェアラブルの案（製品イメージ案の選び方）。

直したこと（`tools/template.html` の `analyzeText`、`tools/guided_data.py` の言葉）
1. カタカナの言葉は、ひらがなで書かれても当てる（「かばん」「Tしゃつ」。3文字以上）。ひらがなの短い言葉は、ひらがなの語の途中に当てない（「玄関においてる」の「におい」）。「30まい」も数量として読む。
2. 入れる物・載せる物・行き先は作る物として読まない（「コーヒー豆を入れるキャニスター」「ドリンクホルダー」「パターのカバー」「ベッドに上がれる階段」「棚を壁につけるための金具」）。会社の並べ方（`relTerms`）・製品DBの当て方でも同じ。
3. 飾りのカタカナ（「デスクライト」の「デスク」）は、すぐ後に別の工程の言葉が続くとき使わない。
4. 材料・加工の言葉とつながる形だけの言葉（「板金のケース」「カバーを革で」）は、材料の工程を優先する。
5. 「1個だけ」だけで読めた試作（3Dプリント）は、布・食品・化粧品・器などの品には付けない。
6. 何も読めないときは、製品仕様DBで品名を当て、その品の工程を使う（設計・試作・組立の決まった3工程に落ちる前に）。
7. 話し言葉の電子機器（「コンセントにさす」「見える化」「知らせてくれる」）、照明器具の完成品メーカー（`tools/makers.py` の `light`、製品名・最初の3行に照明の語があるとき）。
8. 言葉を足した：手ぬぐい・カッパ・扉・フェンス・キーキャップ・アロマオイル・ヨガマット（ゴム）・缶バッジ（バッジの会社）・ぼうし・ししゅう など。

## AI経由（API・MCP）とサイトの一致（2026-11-15）
MCP の search_companies が、サイトの★と違う会社を上位に出していた（例：セントバーナード用スマートカラーで、サイト★アレクソン・Braveridge、MCP 日東商事・東和電機製作所・ユニオンツール）。原因は2つ。
- 本番のAPI（Cloudflare Pages、非公開リポジトリ katachi-data から作る）が PR #108 より前のままだった。katachi-lp を直しても自動では作り直されない → マージ後に katachi-data の `LP_STAMP` を書き換えて作り直す手順にした（AGENTS.md）。
- API は工程と並べ方だけサイトと同じで、★の選び方（完成品メーカー・一社案・組み合わせ案）が別だった → `api/build.mjs` がサイトの画面の JS（`analyzeText`〜`siteTop`、75の宣言）を index.html からそのまま取り出し、API は同じ★を先頭に返す。
- `match_eval.js` が毎回、サイトの★と API の上位3社を比べる（134/134件一致）。違えば PR のチェックが落ちる。
